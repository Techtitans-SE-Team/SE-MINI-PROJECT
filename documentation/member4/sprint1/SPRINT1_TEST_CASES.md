## 1. Basis and implementation notes

Reviewed the SRS requirements baseline, the SRS PDF, backend source and schemas, existing pytest files, SQL schema files, and SQLAlchemy models. The backend currently exposes registration/login, `/auth/me`, patient profile/list/detail, admin, and manual prescription APIs. This document does not add endpoints or claim implementation of SRS features not present in the backend.

The existing pytest suite uses FastAPI `TestClient` with an in-memory SQLite database and dependency overrides. The user-reported suite execution is evidence for the mapped automated cases only; it is not a MySQL-backed integration run. Existing test names are mapped to the specific outcomes asserted by those tests. Where an existing test already exercises the scenario, one formal case covers the related assertions to avoid unnecessary duplicate cases.

Registration and login are implemented in the project, but the SRS does not assign them a functional requirement ID or specify registration/login details. Those test cases are identified as **project testing responsibilities**. Security-related cases use only applicable original SRS IDs such as `NFR-SEC-01` and `NFR-SEC-05`; no new SRS IDs are created.

### Relevant implementation facts used for test design

- `POST /auth/register` accepts Patient or Doctor roles; admin self-registration is rejected by request validation. Patient registration requires name, email, password, date of birth, phone, and preferred language. Doctor registration requires specialization. The code also checks duplicate email and duplicate doctor license number.
- `POST /auth/login` accepts email and password and returns a bearer JWT on success. The same 401 response is used for unknown email and incorrect password.
- `/auth/me` and protected patient, prescription, and admin routes require bearer authentication.
- Passwords are stored using bcrypt hashes. JWT expiry is configured for 60 minutes by default.
- Manual prescriptions use `POST /prescriptions`; doctor-only creation requires an existing active patient. Prescription medicine name, dosage, frequency, duration, date, and patient ID are required. The API rejects blank required medicine fields and future prescription dates. The dosage is text and is preserved as text; the code does not define a clinical dosage grammar or range.
- SQL schema defines roles/users, patients, doctors, and prescriptions with primary/foreign keys and mandatory fields. SQLAlchemy models also define `Medicine` and `PrescriptionFile`; those are Sprint 2 model areas and are excluded from Sprint 1 feature coverage except where the existing manual-prescription test checks a medicine row.

## 5. Coverage gaps and exclusions

### Existing executable automated coverage

- Authentication: successful Patient login, wrong-password/unregistered-user response parity, bcrypt hash persistence, missing/garbage token checks, duplicate email, case-insensitive email, and Admin self-registration rejection.
- Input validation: registration invalid/missing values, Doctor specialization/duplicate license, prescription missing/blank fields, future prescription date, unknown patient during prescription creation, and patient profile validation.
- RBAC/privacy: own patient profile, cross-patient restrictions, doctor-to-patient association, role restrictions, prescription visibility/ownership, Admin prescription-list/verify behaviour, and unknown patient profile lookup.
- Prescription data: valid creation/status, dosage preservation, create-role restrictions, update/verify/lock, rejection, blank update prevention, not-found response, and manual medicine-row synchronization.

### Missing or incomplete coverage

- Login malformed email, missing fields, and empty-password request cases are not directly covered by a dedicated pytest test.
- Expired, tampered, wrongly signed, and malformed JWT variations are not covered; current tests check absent and garbage tokens.
- Whitespace-only registration names, empty registration values, invalid JSON types, and systematic lower/upper boundary values are not covered by pytest; manual cases are included.
- No test establishes a clinical dosage grammar or numeric dosage range. The SRS does not define one; the current API treats dosage as required bounded text and preserves it.
- No existing test connects to MySQL or verifies MySQL foreign-key/unique/NOT NULL behaviour, persistence across new database sessions, backup/recovery, or failure rollback.
- Most pytest API tests use SQLite with foreign-key behaviour that may differ from MySQL; do not use them as proof of MySQL schema integration.
- The SRS's wider reminder, translation, video, and pharmacy features are outside Sprint 1 implementation/test scope here. No tests are created for those unsupported Sprint 1 functions.
- Registration persistence side effects after rejected input are not asserted in several mapped tests; those formal expected results now state only the outcomes their pytest functions actually assert.
- Execution evidence is limited to the user-reported complete-suite summary. Per-test output was not supplied. The 10 manual cases remain Not Executed; no MySQL or frontend/backend/database integration execution is claimed.
